# F. 知識迭代與反思協議

> 目標：讓未來的弱模型能**安全地**自我更新這套 Harness，而不是放任它亂改制度、或永遠不更新導致知識僵化。
> 核心分界：**「記錄事實」可以自己來；「改變規則」要先問人。**

---

## 1. 自改權限分級（動任何 harness 檔前先查這張表）

| 檔案 | 模型可否自行修改 | 條件 |
|---|---|---|
| [`LESSONS.md`](LESSONS.md) | ✅ **可自行追加** | 只能 **append 新紀錄**；**不可刪改他人既有紀錄**；照第 2 節格式 |
| [`journals/*.md`](journals/) | ✅ **各 agent 可自行追加自己那份** | 只能 append 到**自己**的日誌檔；**不可代寫或修改其他 agent 的日誌**；照 [`H`](H-agent-journals.md) 格式，第一人稱 |
| [`E-delegation-templates.md`](E-delegation-templates.md) | 🟡 **可小幅優化** | 只能讓模板更好用（補欄位、修錯字）；**不可放寬驗收嚴格度**；改完在 commit / 回報裡說明改了什麼 |
| [`CLAUDE.md`](../CLAUDE.md) 的「工具鐵律 / 現行真相檔 / 現況」節 | 🟡 **可更新事實** | 僅限「事實變了」的同步（如關卡數、語別數、新增巨檔、新增 agent）；**改鐵律語意要先問人** |
| [`A`](A-diagnosis.md)、[`G`](G-handoff-letter.md) | ⛔ **唯讀** | 歷史文件。要更新另開帶日期的新檔（如 `G2-...`），不覆蓋原文 |
| [`CLAUDE.md`](../CLAUDE.md) 的 🔒 鐵律節、[`C`](C-model-dispatch.md)、[`D`](D-judgment-matrix.md)、[`F`](F-knowledge-iteration.md)（本檔）、[`H`](H-agent-journals.md)、[`appendix`](appendix-recommended-hooks.md) | ⛔ **需先問 User** | 這些是「制度骨架」。改升降級門檻、改熔斷觸發、改部署安全、改自改權限本身、改日誌協議格式本身 → 一律熔斷問人（見 [`D`](D-judgment-matrix.md) 表 3）。**例外**：D 檔允許附加「促升註記」區塊標記過期舉例，不算改規則語意（見 D 檔文末說明） |

> 一句話：**踩坑教訓 = 自己寫；工作日誌 = 自己寫自己那份；規則本身 = 先問人。** 不確定某個改動算哪邊 → 當成「需先問人」。

## 2. 踩坑紀錄寫入格式（寫進 `LESSONS.md`，append-only）

**觸發時機**：任何一次「本來會犯 / 已經犯 / 差點犯」的錯被發現並解決時，就補一條。升級交棒時（見 [`C`](C-model-dispatch.md)）也必須留一條軌跡。

**格式（照抄填空，一坑一條）：**
```
### L-<編號> · <一句話標題> · <YYYY-MM-DD>
- 症狀：<觀察到什麼錯誤/壞結果，含報錯訊息關鍵字，讓下次能搜到>
- 根因：<真正的原因，不是表面現象>
- 正解：<具體怎麼做對，附檔案:行號或指令範例>
- 通則：<抽象成一句可套用到類似情境的規則；若無法一般化寫「個案」>
- 關聯：<[[相關 lesson 編號]] 或指向 CLAUDE.md/harness 某節>
```

- ✅ **完美正例**：
  ```
  ### L-007 · better-sqlite3 要用 .localtools 的 node · 2026-07-03
  - 症狀：node backend/server.js 報 NODE_MODULE_VERSION 不符 / 原生模組載入失敗
  - 根因：系統 node 版本與編譯好的 better-sqlite3 不相容，Windows 無 build tools
  - 正解：改用 .localtools/node-v20.18.1-win-x64/node.exe 執行
  - 通則：本專案所有 node/原生模組指令一律用 .localtools 那支
  - 關聯：CLAUDE.md 工具鐵律表
  ```
- ❌ **典型反例**：「今天 sqlite 壞了，後來好了。」——沒症狀關鍵字、沒根因、沒正解，下次搜不到也學不到。

## 3. 精簡與概念抽象化（防 `LESSONS.md` 膨脹成新的一堆雜訊）

**量化觸發（任一命中即執行精簡）：**
- `LESSONS.md` 超過 **40 條** 紀錄，**或** 檔案超過 **~600 行 / ~40 KB**。
- 或出現 **3 條以上同主題**的坑（例如都在講 Windows 路徑跳脫）。

**精簡動作（這屬於「改制度」等級 → 先跟 User 說一聲再做，做法保守）：**
1. **概念抽象化**：把同主題的多條坑，提煉成 **1 條通則**，升格寫進 `CLAUDE.md` 工具鐵律表或對應 agent，原始細節條目標記 `[已抽象→見 CLAUDE.md X 節]` 但**保留**（不刪歷史，只摺疊）。
2. **歸檔**：把已抽象/過時的條目搬到 `LESSONS-archive-<年>.md`，主檔只留「還活著、還會踩」的坑。
3. **索引**：精簡後在 `LESSONS.md` 頂部維護一行目錄（L-編號 → 標題），方便搜尋。

> 原則：**精簡是「摺疊+升格」，不是「刪除」。** 歷史坑的價值在於「證明這個規則是踩出來的」，不要讓後人重踩。

## 4. 反思節奏（什麼時候該回頭看這套制度）

- **每次踩坑當下**：補 `LESSONS.md`（第 2 節）。這是唯一模型可全自主做的迭代。
- **每完成一個較大任務**：花 30 秒自問「這次有沒有一條坑值得留給後人？有沒有哪條規則其實幫倒忙？」——前者自己寫進 LESSONS；後者**記下來但別自己改規則**，回報 User。
- **命中第 3 節量化觸發**：提請 User 做一次精簡。
- **制度與現實衝突時**：例如某條鐵律已明顯過時 → **不要自己偷偷不遵守**，明確向 User 指出矛盾並建議修訂（熔斷格式，見 [`D`](D-judgment-matrix.md)）。偷偷違規是最危險的腐化起點（見 [`G`](G-handoff-letter.md)）。

## 5. 分工日誌協議（Agent 工作日誌，2026-07-05 User 直接指示新增）

> 這節是 User 在 2026-07-05 明確要求後新增的制度（非模型自行擴權），從此屬於本檔正式內容，往後改動本節本身一樣走上面第 1 節「⛔ 需先問 User」等級。

**規則：每個專責 subagent（小畫家/小工程/小排版/小歌手/小蘋果）完成一項有意義的工作後，用第一人稱在自己的日誌檔追加一條紀錄。**

- 日誌檔位置、格式、寫入時機、完整範例 → 見 [`H-agent-journals.md`](H-agent-journals.md)。
- 這跟 `LESSONS.md` 是**兩件不同的事**：`LESSONS.md` 是「踩坑教訓」（給所有 agent 共用、防重踩），`journals/*.md` 是「某個 agent 自己做過什麼、怎麼想的」第一人稱記錄（給接手同一角色的未來 session 建立連續性、也讓 User 能用角色視角回顧歷程）。兩者不互相取代，都要維護。
- 主對話（指揮官）在派工模板（[`E`](E-delegation-templates.md)）的回報格式裡，可以提醒 subagent「完成後記得寫日誌」，但**不能代替 agent 寫、不能改寫 agent 已寫的內容**——第一人稱敘事的真實性本身就是這個機制的價值，指揮官代筆會讓它失真。
