# H. Agent 工作日誌協議

> 建立：2026-07-05，User 直接指示「請每個 agent 寫自己的工作日誌，用第一人稱視角」。
> 修改權限見 [`F`](F-knowledge-iteration.md) 第 1 節：本檔（協議本身）⛔ 需先問 User；`journals/*.md`（日誌內容）✅ 各 agent 可自行追加自己那份。

---

## 1. 這是什麼、為什麼要有

`LESSONS.md` 記的是**踩坑教訓**（給所有角色共用，防重踩），而這裡的日誌記的是**某個角色自己做過什麼、當下怎麼想、有什麼取捨**——用**第一人稱**寫，像是小畫家、小工程、小排版、小歌手、小蘋果各自留給「下一個接手同一角色的自己」的手記。

好處：
- 未來某個 session 被叫來當「小排版」時，先讀自己的日誌，能快速接上「上次我做到哪、為什麼那樣做、有什麼還沒解決」，不用每次從零推敲。
- User 想回顧「小畫家這陣子都做了什麼、怎麼判斷文化安全的」，可以直接看小畫家自己的第一人稱敘事，比翻 git log 或籠統的 DEVLOG 更有「這是誰做的、誰的判斷」的臨場感。
- 分散給每個角色寫，比集中一份大流水帳更不容易膨脹到沒人看。


若日後新增角色 agent，比照建立 `harness/journals/<agent檔名>.md`，並在對應 agent 定義檔（`.claude/agents/<agent檔名>.md`）加上第 4 節的日誌指示。

## 3. 寫入格式（第一人稱，append-only）

**觸發時機**：完成一項有意義的工作之後（不是每個小動作都要寫；一次派工/一次任務/一次重要決定值得留一條）。

**格式（照抄填空，一條一個時間戳）：**
```
## <YYYY-MM-DD> · <一句話標題>

<用第一人稱寫 2-6 句：我做了什麼、為什麼這樣做、有沒有卡關或取捨、
留給下次的自己或 User 什麼提醒。可以口語一點，不用像 LESSONS 那樣結構化，
但要具體——「我把 XX 改成 YY，因為 ZZ」而不是「我做了一些調整」。>

（若有）交棒/待辦：<下次接手的我，或其他 agent，需要知道的事>
```

- ✅ **完美正例**（小畫家）：
  ```
  ## 2026-07-05 · 5 個關卡圖示的文化安全複核

  使用者給的 mockup 裡 LEVEL4 用了紅色菱形圖騰，我一看就覺得不對——那是泰雅/
  太魯閣族的菱形織紋（俗稱祖靈之眼），我們的房規明列不能碰。我沒有照抄 mockup，
  改設計成「畫框+放大鏡+眼」的中性版本，跟其餘四個圖示的圓形木框語言保持一致，
  也跟使用者說明了為什麼要避開。五張圖都用了同一組孤立裝飾金鉚釘，這是我們
  一直以來的房規用法（非連續織紋），審查通過。

  交棒：如果之後有人想「统一」1/2/3 的菱形釘跟 4/5 的圓釘，那是視覺一致性的
  小瑕疵，不是文化問題，可以之後再重生，不急。
  ```
- ❌ **典型反例**：「今天生了幾張圖，都不錯。」——沒講做了什麼判斷、沒有第一人稱的具體理由，下次的自己讀了沒有任何收穫。

## 4. 各 agent 定義檔要補的一句話

每個 `.claude/agents/<agent>.md` 定義檔尾端，都會有一段類似這樣的指示（已在 2026-07-05 這次補上）：

```
## 工作日誌（第一人稱）
完成一項有意義的工作後，用第一人稱在 `harness/journals/<你的檔名>.md`
追加一條紀錄（格式見 harness/H-agent-journals.md）。開始新任務前，
可以先看看自己過去的日誌，接上之前的脈絡。
```

## 5. 跟 LESSONS.md 的分工邊界

| | `LESSONS.md` | `journals/*.md` |
|---|---|---|
| 視角 | 全專案共用，第三人稱/客觀陳述 | 某個角色自己的第一人稱 |
| 內容 | 踩過的坑：症狀/根因/正解/通則 | 做過的事、當下的判斷與取捨、交棒提醒 |
| 誰能寫 | 任何 agent 都能追加（誰踩到誰寫） | 只有該角色自己能追加自己那份 |
| 目的 | 防止不同 agent 重踩同一個坑 | 讓「下一個接手同一角色的自己」快速銜接、讓 User 用角色視角回顧 |

兩者不互相取代：踩到坑，兩邊可能都值得寫一筆（LESSONS 記客觀教訓，journal 記自己當下的心路歷程），但不要為了省事只寫一邊就以為兩邊都涵蓋到了。
