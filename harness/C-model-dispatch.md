# C. 模型調度與動態升降級守則

> 讀者：主對話模型（指揮官）。目標：用「調度 + 隔離」把弱模型的產出逼近高階品質。
> **本專案真實現況**：主對話 = Opus 4.8；Subagent 預設**繼承** Opus 4.8。故本守則的「成本階梯」目前多半休眠，
> 但**兩個核心價值即使全用 Opus 4.8 也成立**：①把大批量工作丟出主對話→**保護主 context**；②驗收換一顆新腦→**去除確認偏誤**。
> 若日後用 `model` 參數啟用 Sonnet / Haiku，成本階梯自動生效。

---

## 1. 指揮官不下場（Commander does not descend）

主對話模型只做**四件事**：拆任務、下判斷、審結論、跟 User 溝通。以下工作**一律派 Subagent**，主對話只接收精簡結論：

| 工作類型 | 判準（命中就派工） |
|---|---|
| 大批量讀檔 | 要讀的單檔 > 400 行 / > 25 KB，或一次要看 ≥ 3 個檔 |
| Repo 掃描 / 搜尋 | 「這東西在哪」「有幾處用到 X」「盤點所有 Y」這種要掃很多檔的問題 |
| 巨檔（見 CLAUDE.md 巨檔清單） | 任何情況都不整檔讀進主對話 |
| 專業實作 | 落到某個 agent 職責（小工程/小排版/小畫家）的動手活 |
| 隔離驗收 | 見本檔第 4 節，一律派 Fresh-Context Subagent |

**指揮官唯一可以自己讀的**：小檔（< 400 行）、明確要改的那一小段、Subagent 回報的結論。

- ✅ **完美正例**：User 說「排行榜分數沒更新」。指揮官不自己讀 82 KB 的 HTML，而是派小工程：「定位 `hunter-truku-v2.html` 裡分數送出與排行榜刷新的邏輯，回報相關函式名 + 行號 + 你判斷的 bug 點，先不要改。」主對話只收到 3 行結論就能下判斷。
- ❌ **典型反例**：指揮官自己 `Read hunter-truku-v2.html`（整檔進 context），再自己 `Read seed_data.js`，window 燒掉一半才開始想問題出在哪。

## 2. 派工三件套（任何 Subagent 指派都必須包含，缺一不可）

> 完整可套用模板見 [`E-delegation-templates.md`](E-delegation-templates.md)。這裡是**驗收規格**：派工前自檢三件套齊不齊。

1. **明確目標與背景**：這次要達成什麼、為什麼、相關檔案路徑、已知的坑（引用 `CLAUDE.md` / `LESSONS.md` 對應行）。不要只丟一句「修一下排行榜」。
2. **嚴格驗收條件**：怎樣才算做完，寫成可勾選的條件（見 [`D`](D-judgment-matrix.md) 完成定義）。例如「`node --check` 通過 / 本機 3001 打 `/api/scores` 回傳含新分數 / 未觸碰 `scores` 既有筆數」。
3. **標準回報格式**：明令回報「成果檔案路徑 + 關鍵行號 + 一段結論 + 有無殘留風險」，**禁止在回報裡貼大段代碼**（要看代碼指揮官自己去讀那幾行）。

- ✅ **完美正例**（回報）：「已改 `hunter-truku-v2.html:1240-1258`（`submitScore()`）。修正：漏傳 `combo` 欄位。本機 3001 實測送分後 `/api/scores?level=1` 首筆含 combo=7。`scores` 舊筆數 12→13（只新增未改動）。無殘留風險。」
- ❌ **典型反例**（回報）：把整個 `submitScore` 前後 200 行代碼貼回主對話，結論只有一句「應該修好了」——既爆 context 又沒驗證。

## 3. 異常升降級路徑（硬規則，附觸發條件）

> 設定模型的機制：呼叫 `Agent` 工具時帶 `model` 參數（`haiku`/`sonnet`/`opus`/`fable`），或在 agent 定義 frontmatter 寫 `model:`。不指定則繼承主對話模型。
>
> **術語統一（全套制度共用這個定義）**：**「1 輪」= 1 次完整嘗試 + 1 次驗證。上限 = 2 輪**（即最多 2 次「嘗試+驗證」，不是 4 次）。本檔以下、[`D`](D-judgment-matrix.md)、[`E`](E-delegation-templates.md) 講「2 次 / 2 輪」都指這同一個上限。
>
> **本專案預設是 Opus 4.8 起跑**（見本檔開頭）：若你就是 Opus，下表**直接跳到最後一列**（連錯 2 輪 → 熔斷問人）。Haiku/Sonnet 兩列只在你**主動用 `model` 參數**把某個 Subagent 降級跑時才適用。

### 升級（往上，變聰明）
| 現況 | 觸發條件 | 動作 |
|---|---|---|
| Haiku 在跑 | **工具或語法錯 1 次** | 立刻升 Sonnet 重跑（Haiku 不值得為語法坑反覆重試） |
| Sonnet 在跑 | **同一子任務、同一方案連錯 2 輪**（= 2 次嘗試+驗證都失敗） | 升 Opus 4.8，且**必須附完整失敗軌跡**（前兩輪做了什麼、報什麼錯、試過什麼），不要讓 Opus 從零重猜 |
| Opus 4.8 在跑 | 連錯 2 輪仍無解 | **熔斷，停手問 User**（見 [`D`](D-judgment-matrix.md) 熔斷表）。不要無限升級——已無更高常規檔位 |

### 降級（往下，省成本 / 批次套用）
| 現況 | 觸發條件 | 動作 |
|---|---|---|
| Opus 4.8 已解出「固定模式」 | 例如：已確認「把 25 張缺圖依同一 prompt 模板生成」「把 N 個檔案套同一個 rename 規則」 | 把**確定的做法寫成明確步驟**，降回 Sonnet / Haiku **批次套用**，Opus 只做最後抽樣驗收 |

### 全域上限（防止燒 window）
- **同一件事最多重試兩輪**（一輪 = 一次完整嘗試 + 一次驗證）。第三輪不准，改為升級或熔斷。
- 升級時**帶軌跡**是硬要求：`LESSONS.md` 追加一條失敗紀錄（格式見 [`F`](F-knowledge-iteration.md)），再把該條連同上下文交給上位模型。

- ✅ **完美正例**：Sonnet 兩次都在 Windows 路徑跳脫上失敗 → 升 Opus 並附「試過 `C:\\` 與 `C:/` 兩種、報錯訊息如下…」→ Opus 一次點出該用 Bash 工具的 POSIX 路徑 → 把結論寫進 `LESSONS.md` → 之後同類路徑問題降回 Sonnet 照抄。
- ❌ **典型反例**：Sonnet 連錯 4 次還在原地換引號，window 燒光也沒升級，最後回報「做不出來」卻沒留任何軌跡，上位模型只能從零再踩一次同樣的坑。

## 4. 隔離驗證（實作者不得自我驗證）

**鐵律：寫代碼的那個 agent 不准當自己的驗收員。** 驗收一律派**全新 context 的 Subagent（Fresh-Context Subagent）**，它事前不知道實作者「想證明自己對」，因此沒有確認偏誤。

驗收 Subagent 至少做以下一種（依任務性質）：

1. **Read-back 重讀**：獨立打開被改的檔案那幾行，對照「宣稱的改動」與「實際的代碼」是否一致（防「說改了其實沒存 / 改錯地方」）。
2. **實跑測試測資**：真的起 `hunter-backend-local`、真的打 API / 真的截圖，用**具體輸入**驗**具體輸出**（防「讀代碼覺得對，跑起來是錯的」——排版/視覺類尤其必須實跑截圖，見小排版 agent）。
3. **多樣本評審（Multi-agent debate）**：品味/擇優題無單一對錯時，派 2–3 個 Subagent 各自產方案或各自評分，指揮官彙整擇優——但**最終品味拍板仍要回 User**（見 [`A`](A-diagnosis.md) 誠實條款 + [`D`](D-judgment-matrix.md) 熔斷）。

### 驗收 Subagent 的派工要點
- 給它「驗收條件」但**不要**先劇透實作者的結論（避免它照著點頭）。例：「請獨立確認 `hunter-truku-v2.html:1240-1258` 的 `submitScore` 是否會把 combo 一起送出；起本機 3001 送一筆分數，回報 `/api/scores` 首筆是否含 combo，以及 `scores` 表筆數變化。只回報你**實際觀察到**的，不要臆測。」
- 回報格式同三件套：路徑 + 行號 + 實測結果（PASS/FAIL 逐條）+ 有無殘留風險。

- ✅ **完美正例**：小工程改完分數 bug 後，指揮官另派一個 Fresh-Context Subagent 起 3001 實際送分並讀 DB 驗證，回報「PASS：combo 已入庫；scores 舊筆數未變」。
- ❌ **典型反例**：小工程改完自己說「我讀過代碼，邏輯正確，已完成」——沒起服務、沒有人 read-back，直接回報 User，隔天發現根本沒存到檔 / 存錯環境。

## 5. 一頁速查（貼在腦子裡）

```
接到任務
  ├─ 要讀巨檔 / 掃 repo / 專業實作？ → 派 Subagent（帶三件套）→ 只收結論
  ├─ 小改動 / 讀結論 / 下判斷？      → 指揮官自己做
  └─ 做完了？
        └─ 派 Fresh-Context Subagent 隔離驗收（read-back / 實跑 / 擇優）
              ├─ PASS → 回報 User（附證據）
              └─ FAIL → 升級或熔斷；同一事兩輪封頂；踩坑寫進 LESSONS.md
```
