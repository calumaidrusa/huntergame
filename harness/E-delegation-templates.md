# E. 標準化派工 Prompt 模板

> 給指揮官直接套用的委派模板。每份都是**填空題**：把 `<...>` 換掉即可派工。
> 每份都內含「派工三件套」（目標背景 / 驗收條件 / 回報格式，見 [`C`](C-model-dispatch.md) 第 2 節）。
> **共同鐵律**：回報禁止貼大段代碼；只給「路徑 + 行號 + 結論 + 殘留風險」。涉部署/`scores`/品味 → 該 Subagent 也要熔斷回報（見 [`D`](D-judgment-matrix.md) 表 3）。

Context 引入語法（各模板通用開頭，貼在最前面）：
```
先讀 CLAUDE.md 的鐵律與工具鐵律表，以及 harness/D 的完成定義。
本專案已知坑見 harness/LESSONS.md。不要重讀巨檔全文（見 CLAUDE.md 巨檔清單），只讀你需要的那幾段。
```

## 模板 1：搜尋研究（找東西 / 盤點 / 定位，唯讀）

> 適用：「X 在哪」「有幾處用到 Y」「盤點所有 Z」。**指定 Subagent 唯讀，禁止改檔。**

```
<Context 引入語法>

【目標與背景】
我要弄清楚：<要查什麼，例如：排行榜分數送出與刷新的邏輯在哪、以及是否有漏送欄位>。
背景：<為什麼要查 / 這關聯到什麼任務>。相關檔案起點：<檔案路徑，如 hunter-truku-v2.html>。

【範圍與限制】
- 唯讀，禁止修改任何檔案。
- 只讀相關段落，不要把巨檔整檔讀進來。
- 不要臆測；查不到就明說「查無」，不要編。

【驗收條件（你要能回答）】
1. <問題1，如：submitScore 相關函式名與行號>
2. <問題2，如：是否所有欄位都有送出>
3. <問題3，如：有無其他地方也改分數>

【回報格式（照填，禁止貼大段代碼）】
- 結論：<3–5 行內講清楚>
- 證據：<檔案:行號> 逐條對應上面驗收問題
- 不確定/查無：<明列>
- 建議下一步：<一句>
```

## 模板 2：功能實作 / Bug 修復（動手改）

```
<Context 引入語法>

【目標與背景】
要做：<具體功能/修哪個 bug，含重現步驟或期望行為>。
負責角色：<小工程/小排版/小畫家，並說明為何是它>。
已知坑：<引用 LESSONS.md / CLAUDE.md 相關條目，如：hint 欄位不可放內部代號>。

【範圍邊界（防範圍蔓延）】
- 只動：<明確的檔案/函式範圍>。不要順手重構無關代碼。
- 不可碰：scores 表 / onerror fallback / 既有 id·class（JS 依賴）/ 已確立遊戲規則——需要碰就停下熔斷問人。

【驗收條件（做完要逐條滿足，見 harness/D 完成定義）】
- [ ] node --check 通過（若動 .js）
- [ ] 起 hunter-backend-local(3001)，用輸入 <具體輸入> 得到輸出 <具體期望>
- [ ] scores 表筆數/內容前後一致
- [ ] <該任務特有條件>

【重試上限】
同一方案最多 2 次；命中 harness/D 表1 停損信號就停，別原地重試。卡住就帶失敗軌跡回報。

【回報格式】
- 改了什麼：<檔案:行號 + 一句話說明每處改動>
- 自測結果：<逐條驗收條件 PASS/FAIL + 實測輸出>
- 殘留風險：<有/無，說明>
- （我會另派 Fresh-Context Subagent 獨立驗收，請確保你的宣稱經得起 read-back）
```

## 模板 3：代碼重構（不改行為，只改結構）

```
<Context 引入語法>

【目標與背景】
重構目標：<例如：把 hunter-truku-v2.html 裡重複的分數計算抽成一個函式>。
動機：<可讀性/去重/為後續功能鋪路>。**這是重構——對外行為必須完全不變。**

【不變式（Invariant，最重要）】
- 重構前後，<列出必須維持一致的可觀察行為，如：同樣輸入的計分結果、API 回傳格式、畫面外觀>。
- 禁止趁重構改邏輯/改行為/改遊戲規則。發現順便想修的 bug → 另記，不要夾帶。

【驗收條件】
- [ ] 重構前先跑一次基準：<記錄 X 輸入的輸出 / 截圖>
- [ ] 重構後同樣輸入得到完全相同輸出 / 畫面
- [ ] node --check 通過；無新增壞功能
- [ ] 改動集中、可讀性確實提升（否則不值得改）

【回報格式】
- 重構範圍：<檔案:行號>
- 行為不變證明：<前後對照的具體輸入→輸出/截圖>
- 淨收益：<一句：解決了什麼重複/複雜度>
- 殘留風險：<有/無>
```

## 模板 4：代碼審查（挑錯，唯讀）

> 適用：對某段改動或某個檔做獨立審查。也用於**隔離驗收**（見 [`C`](C-model-dispatch.md) 第 4 節）。**先不要劇透你想要的結論，讓它獨立判斷。**

```
<Context 引入語法>

【審查對象】
檔案/範圍：<檔案:行號區間，或某次改動>。
背景（客觀事實，不含結論）：<這段是做什麼的；不要寫「我覺得它對/錯」>。

【審查重點（逐項給判準，禁止「憑感覺」）】
1. 正確性：<用具體輸入推演，會不會有錯誤輸出/crash？舉一個會出錯的情境>
2. 鐵律合規：有無碰 scores 表 / 移除 onerror / 動遊戲規則 / 洩漏 API Key？
3. 環境正確：node 用對版本？shell 語法對平台？路徑跳脫對？
4. <該任務特有風險>

【驗收方式（擇一或多，見 harness/C 第4節）】
- [ ] Read-back：獨立重讀該段，對照宣稱與實際是否一致
- [ ] 實跑：起 3001 用 <具體測資> 驗 <具體輸出>
- [ ] 截圖（視覺類必做）

【回報格式（最嚴重排最前）】
- 判定：PASS / FAIL（逐條驗收條件）
- 發現：<檔案:行號 — 問題一句話 — 會怎麼壞（具體情境）>，最多列你真正確認的，不確定標「疑似」
- 實測輸出：<貼實際觀察，不是臆測>
- 若 FAIL：最小修正建議（一句，不要動手改）
```
