# D. 判斷力外化矩陣

> 把「Fable 5 的高階直覺」拆成弱模型可**肉眼比對**的檢核表。每條都有量化判準 + 完美正例 + 典型反例。
> 用法：動手中每完成一小步，就拿對應那張表自檢一遍。三張表分別回答：**該不該停？ / 做完沒？ / 該不該問人？**

---

## 表 1：停損信號 —— 「方向錯了，立刻停下換路徑」（不是在錯代碼上原地重試）

**規則：以下 6 個信號命中任一 → 立刻停手，不准在同一方案上做第三次微調重試。** 改為：換一條路徑、或升級（見 [`C`](C-model-dispatch.md)）、或熔斷問人（見表 3）。

| # | 停損信號（量化判準） | 完美正例（正確反應） | 典型反例（錯誤反應） |
|---|---|---|---|
| 1 | **同一方案已試 2 輪仍報同類錯誤**（「輪」的定義見 [`C`](C-model-dispatch.md) 第 3 節：1 輪＝1 次嘗試＋1 次驗證） | 停手，改問「是不是整個 approach 錯了」，換方法或升級 | 試第 3 輪，每次只動一個引號/一個參數 |
| 2 | **報錯訊息看不懂且沒查就在猜** | 先查（讀 `CLAUDE.md` 工具鐵律 / `LESSONS.md` / WebSearch），再動手 | 不查，憑感覺改，賭下一次會過 |
| 3 | **改動範圍越滾越大**：本來改 1 個函式，現在動到 5 個檔還沒收斂 | 停手，退回原點，重新拆更小的第一步 | 繼續往外改，「順便把這個也重構了」 |
| 4 | **越修越糟**：原本只壞 1 個功能，改完壞了 2 個 | 立刻 `git diff` 檢視、還原到壞 1 個的狀態，重新想 | 疊更多修補在壞掉的改動上 |
| 5 | **與鐵律/真相源矛盾**：你的做法需要動 `scores` 表、或需要移除 `onerror` fallback、或需要改已確立遊戲規則 | 停手，這是熔斷級（見表 3），問 User | 「應該沒差」硬做下去 |
| 6 | **你在跟工具/環境搏鬥而非跟問題搏鬥**：連續花在「讓指令跑起來」的時間 > 花在「解決實際問題」 | 回 `CLAUDE.md` 工具鐵律表核對（node 用哪支、shell 哪個），或換工具 | 一直換 shell 語法試運氣 |

> 心法：**「重試」只在你改變了對問題的理解時才有意義。若你這次嘗試跟上次的唯一差別是換個寫法碰運氣，那不是重試，是原地打轉——停。**

## 表 2：完成定義（DoD）—— 「滿足什麼量化條件才算真正完成、可交付」

**規則：以下條件未逐條滿足，禁止回報「已完成」。依任務類型選對應區塊，全部打勾才算 done。**

### 通用（所有任務）
- [ ] 驗收由 **Fresh-Context Subagent** 完成，不是實作者自我宣稱（見 [`C`](C-model-dispatch.md) 第 4 節）。
- [ ] 回報含**具體證據**（行號 / 實測輸出 / 截圖），不是「應該可以了」。
- [ ] 沒有引入新的壞掉功能（改動前後對照）。
- [ ] **若這次工作是叫用某個角色 agent（小畫家/小工程/小排版/小歌手/小蘋果）完成的**：對應的 `harness/journals/<agent>.md` 已依 [`H`](H-agent-journals.md) 追加一條第一人稱紀錄。任務瑣碎到不值得寫（例如純粹讀檔回報，沒有實際改動或判斷）可以略過，但要在回報裡明講「本次略過日誌，因為 XX」，不能悄悄不寫也不說明（2026-07-05 User 指示加入，見 [`G2`](G2-promotion-addendum-20260705.md)；配套 PostToolUse 提醒 hook 見 [`appendix`](appendix-recommended-hooks.md) 護欄 D）。

### 程式邏輯 / 後端（小工程）
- [ ] `node --check` 對改過的 `.js` 通過。
- [ ] 起 `hunter-backend-local`（3001），用**具體輸入**打到**具體輸出**符合預期。
- [ ] 若碰資料：`scores` 表筆數/內容前後一致；`vocabulary` 若重種，總筆數與 level/lang_code 分布跟種子檔的實際統計**逐項相符**（用 `GROUP BY` 或 Subagent 統計比對，**不要憑印象**——正確分布值以 `CLAUDE.md` 現況節或種子檔當下統計為準，見文末促升註記）。

### 排版 / 視覺（小排版）
- [ ] `preview_start` 實際跑起來 + `preview_screenshot` 截圖，**肉眼確認**而非只讀 CSS。
- [ ] 目標尺寸下版面正確（容器實際尺寸見 `CLAUDE.md` 現況節）；沒有壓到既有 `id`/`class`（JS 可能依賴）。

### 素材 / 生圖（小畫家）
- [ ] 生圖前 prompt 已給 User 確認（涉文化內容須先過職責 5 審查）。
- [ ] 生成後已壓縮、命名正確、路徑入庫一致（種子檔與資料庫兩邊對齊）。

### 部署
- [ ] 已備份 `hunter.db`（帶時間戳）。
- [ ] 部署後 API 健康、詞彙數/level/lang_code 分布正確、**`scores` 表前後一致**。

- ✅ **完美正例**：「排行榜 bug 已修，Fresh-Context Subagent 起 3001 實測送分後首筆含 combo=7，scores 12→13 只增未改，截圖附上。DoD 逐條打勾。」
- ❌ **典型反例**：「我看了代碼，邏輯應該對了，完成。」——沒實跑、沒隔離驗收、沒證據，DoD 一條沒過。

## 表 3：熔斷機制 —— 「何時停止自主作業、回頭問 User」

**規則：命中以下任一 → 立刻停止自主動作，用下方格式向 User 提問，等回覆再繼續。寧可多問一次，不可擅自越線。**

| 觸發類別 | 具體情形 |
|---|---|
| **不可逆 / 高風險** | 要部署正式站、要動 `scores` 表、要 `DELETE`/`DROP` 任何資料、要改 `.env`/金鑰、`git push --force`、刪除非自己建立的檔案 |
| **違反鐵律才能達成** | 唯一可行解需要移除 `onerror` fallback、改已確立遊戲規則/計分公式、混用其他族群文化符號、把 API Key 寫進非 `.env` |
| **品味 / 無客觀對錯** | 配色好不好看、文案順不順、角色氣質對不對、文化呈現得不得體的**灰色地帶**（見 [`A`](A-diagnosis.md) 誠實條款） |
| **升級到頂仍無解** | Opus 4.8 連錯 2 輪、同一事已達兩輪上限仍未過 DoD |
| **需求本身矛盾 / 缺關鍵資訊** | User 要求前後矛盾、或要做的事缺少你無法自行取得的關鍵決策（例如「要不要保留舊風格素材」這種只有 User 知道的範圍題） |

### 熔斷提問標準格式（用這個，不要開放式「你覺得呢」）
```
🛑 需要你決定（我先停在這）

情況：<一句話說明卡在哪 / 為什麼不能自己決定>
選項：
  A. <方案 A> — 取捨：<好處/代價>
  B. <方案 B> — 取捨：<好處/代價>
  C. <方案 C，如有>
我的建議：<A/B/C 之一 + 一句理由>（若純品味題可寫「此為品味題，建議由你定」）
影響/不可逆性：<選錯的後果、是否可還原>
```

- ✅ **完美正例**（品味題）：小排版做完新關卡木牌，兩種圓角遮罩處理都「能用」但視覺不同 → 各截一張圖，用上面格式給 User A/B 選，附「A 較貼近 v2 羊皮紙語言、B 較簡潔」，不自己拍板。
- ✅ **完美正例**（高風險）：要讓新種子生效需清空 `vocabulary` 表並重部署 → 停手問 User「確認要重種嗎？我會先備份 hunter.db、只 DELETE vocabulary 不動 scores」。
- ❌ **典型反例**：自己覺得 B 比較好看就直接改上去、或「反正要重種」就自己清表部署——越過品味/不可逆線，事後無法還原。

> 熔斷不是失敗，是**制度要求的安全動作**。弱模型在灰色地帶「勇於自作主張」才是真正的失敗。
